# Seller enquiry workflow

Status: **All four phases written. Not production-ready; see "Launch blockers". Operations and deployment: `docs/SELLER_OPERATIONS_RUNBOOK.md`.** See "Verification status" below.

## Phase plan
1. (done) Public `/sell-a-casino`, `POST /api/sell-a-casino`, persistence, references, seller acknowledgement and internal alert emails, audit append-only protection.
2. (done) Staff inbox, assignment, transition matrix, notes, communications, qualification, follow-up tasks and reminders.
3. (done) Seller records, authority/mandate review, conversion to a private draft opportunity, server-side publication gates.
4. Seller follow-up and material-interest approval flows, retention review, runbook completion.

## What Phase 1 does
- `GET /sell-a-casino` renders the form (no upload, no account). Submission is JSON via `public/static/js/sell-form.js`; the page needs JavaScript (also required by Turnstile). The browser never puts form data or the reference in a URL.
- `POST /api/sell-a-casino`: JSON only, 32 KB limit, Turnstile (existing middleware, fail-closed outside dev), per-IP rate limit (5 per 10 minutes, KV, keyed hash of IP), honeypot, Zod validation shared in `src/seller/schema.ts`, unknown fields stripped (project policy).
- Idempotency: the browser sends a per-page-load key; only its HMAC is stored (`idempotency_hash`, UNIQUE). A repeat gets the same neutral 202 and reference and inserts nothing.
- Reference `CM-S-XXXXXX` from a CSPRNG, UNIQUE in the database, retried on collision.
- One D1 batch writes the enquiry (status `NEW`), an audit row, and two `notification_jobs` rows (the durable outbox) with logical keys `seller_enquiry_ack:<id>` and `seller_enquiry_internal_alert:<id>` (unique index `idx_notification_jobs_dedupe`). Enqueue happens afterwards; if it fails, the existing 5-minute recovery cron re-enqueues.
- Email: `seller_enquiry_received_v1` and `seller_enquiry_internal_alert_v1` (HTML + plain text, escaped). 4xx provider errors other than 408/429 are permanent and go straight to `dead`; others use the existing backoff (max 5 attempts). **"sent" means accepted by Resend, not delivered to an inbox.**
- Original submission is preserved in `original_submission_json`; later edits belong on seller records (Phase 3).
- Raw IPs and anti-abuse tokens are never stored.

## Phase 2: staff workflow
- UI: `/dashboard/seller-enquiries/ui` (menu: Seller enquiries). List shows reference, name/organisation, status, asset, owner, next follow-up, received date; no email, phone or free text. Search matches reference, name, organisation or email. Filters: status, broker (incl. unassigned), asset type, country, received date range, follow-up overdue/due today. 25 per page.
- API (all under `/dashboard`, JSON): `GET /seller-enquiries`, `GET /seller-enquiries/:ref`, `POST /seller-enquiries/:ref/{assign,status,notes,communications,followups,qualification}`, `POST /seller-enquiries/:ref/followups/:taskId/complete`. Staff URLs use the public reference, not the database id; the id is stripped from responses. Unknown, malformed and out-of-scope references all return the same 404.
- Access: brokers see and work only enquiries assigned to them; admin/super_admin see all. Assignment, decline and close are manager-only (`seller_enquiries.assign` / `.close`). Editors, publishers and auditors have no seller access. There is **no separate compliance role**: authority review (Phase 3) will map to admin. New permissions are in `src/permissions/permissions.ts`; route role lists in `src/admin/shared.ts`; `docs/ROLE_ROUTE_MATRIX.md` regenerated.
- Lifecycle (`src/seller/lifecycle.ts`, enforced server-side): NEW→ASSIGNED|CONTACT_ATTEMPTED; ASSIGNED→CONTACT_ATTEMPTED; CONTACT_ATTEMPTED→AWAITING_SELLER|QUALIFICATION; AWAITING_SELLER→CONTACT_ATTEMPTED|QUALIFICATION; QUALIFICATION→AWAITING_SELLER|AUTHORITY_REVIEW|QUALIFIED; AUTHORITY_REVIEW→QUALIFICATION|QUALIFIED; QUALIFIED→CONVERTED; every open status→DECLINED|CLOSED. DECLINED, CLOSED and CONVERTED are terminal. Rules: decline/close need a reason (5+ characters) and confirmation; QUALIFIED, AUTHORITY_REVIEW also need confirmation; progressing needs an owner; QUALIFIED needs a recorded PASS qualification review; ASSIGNED only via the assign action; **CONVERTED is not reachable through the status endpoint** (explicit conversion arrives in Phase 3).
- Concurrency and atomicity: status/assignment changes use `version` optimistic locking; the history and audit rows are written in the same D1 batch and only if the row changed (`WHERE changes() > 0`). A stale request gets 409 `VERSION_CONFLICT`.
- Records (migrations 0034/0035; append-only by trigger): staff notes (audit stores id and classification, never text), communications, status/assignment history, qualification reviews (11-item checklist; "compliance routed" records only that the matter was sent to your legal/KYC/AML process, never that checks passed). The acknowledgement email is recorded as a system communication marked "accepted by provider".
- Follow-ups reuse `staff_tasks` (`related_entity_type = 'seller_enquiry'`, plus type/outcome/reminder/escalation columns), so they also appear on the existing Tasks page. A broker can only schedule follow-ups for themselves. Completing a task checks it belongs to the enquiry in the URL.
- First response: set when the first human outbound communication is recorded (the automatic acknowledgement does not count).
- Reminders (`seller_followup_due_v1`): the existing cron runs `runSellerReminders`; one job per task per reminder window and one escalation per task, enforced by the unique `dedupe_key`. Completed or closed-out work is skipped at send time. Configuration: `SELLER_REMINDERS_ENABLED` (default on; `false` disables), `SELLER_REMINDER_INTERVAL_HOURS` (default 24), `SELLER_ESCALATION_AFTER_HOURS` and `SELLER_ESCALATION_RECIPIENTS` (escalation off unless both set). These are environment settings, not a dashboard screen. Nothing here is a commitment to sellers.

## Phase 3: sellers, authority, conversion, publication gates
- **Sellers** (`/dashboard/sellers/ui`; table `sellers`, reference `CM-C-XXXXXX`): created explicitly from an enquiry at QUALIFICATION or later, with an owner assigned; contact details are copied from the stored enquiry (never client input). A manager can instead link an enquiry to an existing seller; the matching-email list is only a hint and nothing is ever merged automatically. Brokers see only sellers they own. Corrections go through `POST /sellers/:ref/update`, need a reason and a version, and keep old and new values in append-only `seller_changes`. Multiple contacts per seller are **not** implemented (deferred).
- **Authority and mandate** (`seller_authority_records`, reference `CM-A-XXXXXX`, attached to a seller-opportunity link): five separate types (submit, represent, negotiate, market, brokerage mandate); none implies another. States: NOT_REVIEWED, EVIDENCE_REQUESTED, UNDER_REVIEW, VERIFIED, REJECTED, EXPIRED, REVOKED, NOT_REQUIRED_WITH_RECORDED_REASON, with an enforced transition matrix (`src/seller/authority.ts`). Brokers can only record a claim (it starts NOT_REVIEWED); review and approval are manager-only. VERIFIED needs recorded evidence type and scope; NOT_REQUIRED needs a written reason; both need confirmation. **Separation of duties:** the person who recorded a claim cannot verify it (default on; `SELLER_SEPARATION_OF_DUTIES=false` disables, which a single-admin team will need). Evidence is a **reference** to private storage or your compliance system (no URLs); no evidence files are stored or served by this feature. A validity window is honoured live and by a scheduled sweep that marks lapsed records EXPIRED.
- **Conversion** (`POST /seller-enquiries/:ref/convert`): only from QUALIFIED with a linked seller, with confirmation and the enquiry version. In one transaction it creates a draft opportunity (confidential, unreviewed, not public, staff-written neutral title, no enquiry text copied), links it to the seller, sets the enquiry to CONVERTED with history, and writes two audit rows. Creating a seller never converts an enquiry. Existing private opportunities can be linked with `POST /sellers/:ref/links`; a live listing cannot be linked.
- **Publication gates for seller-sourced opportunities** (any opportunity that has ever had a seller link): every active seller relationship needs reviewed confidentiality restrictions, a currently valid VERIFIED (or NOT_REQUIRED with reason) authority to market and brokerage mandate, and an APPROVED publication review (scope, confidentiality, public fields, sensitive data, image rights, legal review, all confirmed; approver differs from preparer by default). Enforced three ways: the two existing publication endpoints return 409 `SELLER_GATES_NOT_MET` with the unmet list; a database trigger (`trg_opportunities_seller_publication_gate`) blocks any other path that tries to make such a row public or published; and approval itself refuses while authority gates are unmet. Approval never publishes; the normal publication workflow still applies on top. Existing and imported listings with no seller link are unaffected.
- **Withdrawal:** revoking a publication review, or revoking/expiring a marketing authority or mandate (unless another valid record of that type covers the link), takes any live dependent listing off the website in the same transaction, writes an audit row, and purges the public cache. Ending a seller relationship is blocked while the listing is live and leaves the opportunity under the gates.
- **New routes** (all role-guarded, see `docs/ROLE_ROUTE_MATRIX.md`): `/sellers/ui`, `GET /sellers`, `GET /sellers/:ref`, `POST /sellers/:ref/{update,links}`, `POST /sellers/:ref/links/:linkId/{review,end,authority}`, `POST /authority/:ref/transition`, `GET /opportunities/:id/seller-gates`, `POST /opportunities/:id/seller-publication-review`, `POST /seller-enquiries/:ref/{seller,convert}`, `GET /seller-enquiries/:ref/seller-candidates`.
- **Migrations:** `0036` (tables; additive) and `0037` (append-only and publication-gate triggers). Rollback: drop the listed triggers; tables can stay.
- **Permissions:** `sellers.*`, `authority.*`, `opportunities.create_draft`, `opportunities.approve_publication` added. Publication approval roles are admin, publisher and super_admin; verification is admin and super_admin.

## Phase 4: staff-sent email, material interest, privacy
- **Staff follow-up** (`seller_enquiry_followup_v1`): the broker enters 1 to 8 questions and a title; the system renders the exact email and shows it for confirmation; only then is it queued. Content is frozen and SHA-256 hashed at approval; a database trigger refuses later edits and the dispatcher re-checks the hash. The recipient must still match the enquiry email at send time. Double-clicks cannot create a second send (unique outbox key). A queued message can be revoked until it starts sending. "Sent" means the provider accepted it; inbox delivery is not confirmed. A failed job shows as "SENDING FAILED" and is handled through the notification monitor.
- **Material interest** (table `seller_material_interests`, reference `CM-M-XXXXXX`): recorded by a broker against an active seller relationship; internal fields (summary, buyer reference) are never emailed. Stages: RECORDED, UNDER_REVIEW, APPROVED, REJECTED, WITHDRAWN, NOTIFIED. Only an approver (admin/super_admin) can approve, reject or withdraw. Approval requires reviewed, staff-written seller-facing text (summary, stage wording, next step), recorded confidentiality review, and **entitlement**: an active relationship with reviewed confidentiality and a currently valid VERIFIED (or NOT_REQUIRED with reason) authority to represent or brokerage mandate. Interest types are labels, not legal equivalents; a FORMAL_OFFER record is still just a record.
- **Material-interest notice** (`seller_material_interest_v1`): draft, preview of the exact email, then approve-and-send by an approver with recent MFA. The email contains only the approved fields: no buyer identity, terms or finance. Optional second approver: `SELLER_MATERIAL_INTEREST_DUAL_APPROVAL=true` (default **off**, because the business has not adopted dual approval). Before dispatch the worker re-checks: message still queued, content hash, interest still APPROVED and unchanged since the draft, seller still entitled, seller email unchanged. Any failure cancels the message with an audited reason and sends nothing. Withdrawing the interest cancels draft and queued notices in the same transaction. Sending moves the interest to NOTIFIED; a second notice for the same approved interest is refused.
- **Privacy:** `/dashboard/seller-privacy/ui` (admin and super admin). Retention: candidates (declined or closed, unlinked, not held) are listed **only if** `SELLER_RETENTION_REVIEW_DAYS` is set; the system assumes no period. Anonymisation is irreversible and needs recent MFA, a typed reference, a reason, no legal hold, no seller link, and a declined/closed enquiry. It removes personal data and redacts staff free text (notes, communication summaries, history reasons, qualification text, task titles, sent message content); structure (reference, dates, status, country, asset type) and the audit log are kept. Append-only tables permit exactly one kind of change: replacing text with `[redacted]`. Legal holds block anonymisation. Privacy requests (access, erasure, rectification, restriction, marketing withdrawal) are logged with a due date entered by staff (no statutory period is assumed) and closed with an outcome note. Marketing-consent withdrawal is recorded without affecting the enquiry. Export (`GET /seller-enquiries/:ref/export`) is super admin only, needs recent MFA, is never cached, is audited without its content, and excludes message bodies.
- **Step-up (MFA) now also protects** authority verification and revocation (Phase 3 route), material-interest sending, anonymisation and export.
- **Migrations:** `0038` (additive tables and columns), `0039` (triggers; replaces three append-only triggers with redaction-aware versions). Rollback is in the file header.
- **Permissions added:** `seller_communications.send`, `seller_material_interest.{record,approve,send}`, `seller_retention.manage`, `seller_enquiries.export`. `seller_audit.read` is covered by the existing audit permission and screen (seller audit details contain no personal data by design).

## Gap closure (after Phase 4)
- **Seller erasure:** `POST /sellers/:ref/anonymise` (admin or super admin, recent MFA, typed reference, reason). The seller must already be INACTIVE. One database statement carries every precondition (no active relationship, no live or published listing, no open, held or non-terminal enquiry, no open material interest, no legal hold) and every redaction is guarded on it. It clears the seller, its enquiries, additional contacts, correction history, authority scope and notes, interest text and buyer reference, staff notes, communication summaries, task titles and sent-message text. Authority records stay VERIFIED/REVOKED with `[redacted]` scope so constraints still hold. Seller legal hold: `POST /sellers/:ref/legal-hold`.
- **Additional contacts:** `seller_contacts` (add, soft-remove) on the seller screen. They are informational: notices still go only to the primary contact. They are included in erasure.
- **Assignment email** (`seller_enquiry_assigned_v1`): the new owner is emailed (not on self-assignment), from the same transaction as the assignment, through the outbox with key `seller_assignment:<enquiry>:<version>`; skipped if the enquiry was reassigned before it ran. It carries reference, status, asset type and country, confidentiality preference and the dashboard link only.
- **Denied-action audit:** every 403 from a seller route (role refusal or missing step-up) is written to `audit_logs` as `seller.permission_denied` or `seller.step_up_required`, with the method, role and the route shape (identifiers replaced). Out-of-scope records still return 404 and are deliberately not logged as denials.
- **MFA on close and decline:** now required (in addition to the manager role).
- **Export** now includes the text of emails sent about the enquiry.
- **Browser tests:** `e2e/tests/seller-workflow.spec.ts` (not executed; see `e2e/README.md`).
- **Migration `0040`:** `seller_contacts` and redaction-aware triggers for authority and interest events.

## Not yet built
- Evidence file upload and secure retrieval (authority evidence is still a reference only). This needs a product decision and the existing scanner and private storage to be configured; it is not safe to add blind.
- A separate compliance role (authority review remains admin-only). Adding a role touches the role model used across the dashboard and its tests, so it needs your decision and a full test run.
- Dashboard-editable policy and reminder settings (these are environment configuration).
- Full-journey browser automation of staff approvals (needs MFA, two approvers and real email).
- Retention that runs automatically (deliberately staff-driven).
- Anonymisation of opportunities and publication records (they hold staff-written neutral text, not seller personal data).

## Known limitations
- Turnstile hostname/action validation is not added (shared verifier in `turnstile-core.ts` unchanged).
- Per-session rate limiting is not implemented; only per-IP.
- No automatic duplicate detection beyond the idempotency key (by design: no merging by email or asset name).
- Privacy notice version is the version of the acknowledgement text (`seller-form-privacy-ack-v1`); it is not linked to the managed `/legal/privacy` page revision. Legal must review that page before launch.

## Notes from applying Phase 1
- Migration 0033 (append-only `audit_logs`) made four existing tests fail because their cleanup deleted audit rows (`buyer-download-e2e`, `password-auth`, `staff-mfa`, `portal-repo`). They were fixed by dropping the trigger inside the test database before cleanup. Consequences: (a) after those tests run, the trigger is gone for the rest of that test database, so no test currently proves it holds; (b) production code, scripts, workflows and docs contain no update or delete of `audit_logs` (searched), so the trigger does not affect runtime. If you ever add an audit-retention job, it will need a deliberate, audited exception to this trigger.
- Strict compiler flags (`exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`) and the `no-control-regex` lint rule apply to this code; Phase 2 follows the same fixes you made after Phase 1.
